# skydio_me_node — Skydio X10D Mission Executor

This is an MPMS Mission Executor (ME) node. Its job is to take an abstract MPMS
`TraverseTo` command ("fly this list of waypoints") and turn it into the concrete,
native messages the Skydio X10D drone actually understands — the RAS-A/MAVLink v2
protocol described in Skydio's "X10D Control and Telemetry ICD".

In other words: MPMS mission software sends a waypoint list to this node, and this
node speaks MAVLink over UDP to the drone to upload the route, arm the drone, start
the mission, monitor progress, and report back when the traverse is complete.

## How the code is organized

Following the MPMS Integration Toolkit workflow, the repo separates **generated
code** from **developer-written code**:

- `gen_include/` and `gen_src/` — interfaces generated by the MPMS toolchain from
  the behavior/asset definitions. These are never edited by hand. They define the
  signals (`start`, `update`, `pause`, `resume`, `stop`), the config parameters,
  and the asset telemetry fields the node must publish.
- `include/` and `src/` — the developer-written implementation, described below.

## What each implementation file does

**`src/SkydioMavlinkClient.cpp`** (with `include/SkydioMavlinkClient.h`) is the
low-level driver that talks to the drone. It is a self-contained MAVLink v2
implementation (no external MAVLink library needed) that handles:

- Opening a UDP socket to the X10D and exchanging heartbeats to establish that
  the link is alive.
- Encoding and decoding MAVLink v2 frames, including the checksum (CRC) that
  every message carries so corrupted packets are detected and dropped.
- The **mission upload handshake**: the node announces how many waypoints it has
  (`MISSION_COUNT`), the drone asks for each one, the node answers with a
  `MISSION_ITEM_INT` per waypoint, and the drone confirms with `MISSION_ACK`.
  Lost packets are retransmitted and the whole exchange retries on timeout.
- Sending **commands** (`COMMAND_LONG`) such as arm, start mission, pause,
  resume, and change speed — each one waits for the drone's acknowledgement
  (`COMMAND_ACK`) and retries if no answer arrives.
- Decoding **telemetry** (`GLOBAL_POSITION_INT`) into latitude, longitude,
  altitude, heading, and speed, and tracking mission progress messages
  (`MISSION_ITEM_REACHED`, `MISSION_CURRENT`) so the behavior knows which
  waypoint the drone has reached.

**`src/TraverseTo_impl.cpp`** is the behavior logic — the "brains" that map each
MPMS signal onto a sequence of drone actions:

- `start` — parse the waypoint list (GeoJSON) from the signal data (or fall back
  to the `waypoint_list` config parameter), build a flight plan (takeoff item,
  speed setting, then one waypoint item per point), upload it to the drone, arm
  the drone if needed, and command `MISSION_START`. A background worker thread
  then watches telemetry and fires the `WaypointListComplete` output signal when
  the drone reports reaching the final waypoint.
- `update` — pause the current mission, upload the new waypoint list, and restart.
- `pause` / `resume` — send `MAV_CMD_DO_PAUSE_CONTINUE` with param1 = 0 (hold in
  place) or 1 (continue the mission).
- `stop` — hold in place, then clear the uploaded mission with
  `MISSION_CLEAR_ALL`.

All waypoint input is validated before use — malformed or empty GeoJSON is
rejected safely rather than crashing the node — and the commanded speed is
clamped to the configured `[minVelocity_mps, maxVelocity_mps]` range.

**`src/skydio_me_nodeAsset_impl.cpp`** publishes the asset parameters MPMS
requires (`position`, `altitude`, `heading`, `speed`), updated at 10 Hz from the
drone's live telemetry.

**`src/main_skydio_me_node.cpp`** is the entry point: it reads the config file,
starts the MPMS communication interface, connects the MAVLink client, and runs
the telemetry loop.

**`src/utility.cpp`** contains helpers for parsing GeoJSON/WKT waypoint lists,
reading the config file, and geometry math.

## What the tests cover

The test suite (`tests/`, GoogleTest) runs entirely on your machine — no drone
and no proprietary MPMS SDK needed. The SDK headers the behavior code uses are
stubbed under `tests/stubs/`, and the drone is simulated by
`tests/FakeVehicle.h`: a fake vehicle on a loopback UDP socket with its own
independent MAVLink decoder (a separate CRC implementation), so an encoding bug
in the production code cannot accidentally verify itself.

- **`test_mavlink_client.cpp` — the protocol layer.** Verifies the driver's
  wire behavior against the ICD: correct MAVLink v2 framing, CRCs, and sequence
  numbers; heartbeat exchange and link-health timeout; the full mission upload
  handshake including the legacy `MISSION_REQUEST` variant, duplicate/lost
  requests, retransmission of lost items, vehicle rejection, and retry
  exhaustion; command encoding and acknowledgement handling including
  `IN_PROGRESS` acks, rejections, and unacked retries; mission clear with
  lost/rejected acks; telemetry decoding (including the "heading unknown"
  sentinel); and survival of malformed or corrupted frames.
- **`test_traverse_to.cpp` — the behavior layer.** Drives the real signal
  handlers end-to-end against the fake vehicle: a full
  start → upload → arm → start → complete lifecycle; completion fires only on
  the *final* waypoint and only once; pause/resume map to the right command and
  don't falsely complete; stop holds, clears, and prevents a later stale
  completion; update re-uploads a new plan; empty or malformed waypoint input
  is rejected without side effects; speed is clamped to the configured bounds;
  and repeated start/stop cycles stay consistent.
- **`test_utility.cpp` — the helpers.** GeoJSON parsing for Point, LineString,
  and Polygon features (including malformed input), WKT parsing, config-file
  parsing (including a last line with no trailing newline), and geometry math.

### Running the tests

Requires CMake, GoogleTest, and GDAL dev packages:

```sh
cmake -S tests -B build-tests
cmake --build build-tests -j
ctest --test-dir build-tests --output-on-failure
```

## How MPMS signals map to drone messages

| MPMS `TraverseTo` signal | What the node sends to the X10D |
|---|---|
| `start` | Mission upload (`MISSION_COUNT` → `MISSION_ITEM_INT` per waypoint → `MISSION_ACK`), then `MAV_CMD_COMPONENT_ARM_DISARM` (arm) and `MAV_CMD_MISSION_START` |
| `update` | Hold in place, upload the new waypoint list, restart the mission |
| `pause` / `resume` | `MAV_CMD_DO_PAUSE_CONTINUE` with param1 = 0 (hold) / 1 (continue) |
| `stop` | Hold in place, then `MISSION_CLEAR_ALL` |
| `WaypointListComplete` (output) | Fired when `MISSION_ITEM_REACHED` reports the final waypoint |

## Building and configuring the node

Building the real node requires the MPMS SDK (`MMSLib`, `MMSTypes`,
`UDPCommInterface`), nlohmann/json, and GDAL. Compile everything under `src/`
and `gen_src/` with `include/` and `gen_include/` on the include path.

Runtime settings live in `skydio_me_node.cfg`:

| Key | Default | Meaning |
|---|---|---|
| `SKYDIO_VEHICLE_IP` | `192.168.42.10` | IP address of the X10D control link |
| `SKYDIO_VEHICLE_PORT` | `15667` | UDP port the X10D listens on for MAVLink |
| `SKYDIO_LOCAL_PORT` | `14551` | Local port this node binds for MAVLink |
| `SKYDIO_GCS_SYSTEM_ID` | `255` | MAVLink system id this node identifies as |
| `SKYDIO_TARGET_SYSTEM_ID` | `1` | MAVLink system id of the X10D |
| `UDP_RX_PORT`, `UDP_HOSTS_FILE` | `5001`, `./hosts.json` | MPMS-side communications |

## Testing that still requires hardware

The unit and protocol tests above are fully automated locally. What they cannot
prove is how a *real* X10D responds, so two verification stages remain (details
in [docs/TEST_PLAN.md](docs/TEST_PLAN.md)):

1. **Bench hardware-in-the-loop** (a real X10D with propellers removed):
   confirm the actual vehicle accepts the mission upload, the coordinate frame
   and takeoff item, and behaves as expected for hold/clear.
2. **Live flight**: fly a full waypoint traverse and exercise
   pause/resume/update/stop and the completion signal in the air.
